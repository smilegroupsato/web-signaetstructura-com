## 1. Purpose

SIGNA ET STRUCTURA is the public publication surface for market research, data, figures and recurring market observations produced from the SC asset-management research system.

Editorial direction:

**Financial Times × academic journal × modern data publication**

Editorial principle:

**Signal → Structure → Evidence**

The public repository contains only public-safe artifacts. Internal research, portfolio decisions, raw confidential evidence, execution state and secrets remain outside this repository.

## 2. Source-of-truth boundary

```text
smilegroupsato/sc-crypto-ops
  Research / Evidence / patrol observations
  public-draft / publish classification
  internal Gate / review / approval
             ↓ public-safe package
smilegroupsato/web-signaetstructura-com
  public registries
  public article editions
  public figures / data
  Publication Builder
             ↓ generated site candidate
             ↓ ordinary Research: explicit human publish request
             ↓ approved auto-series: automatic fail-closed gate
signaetstructura.com
```

Executed investment decisions and internal Candidate / Portfolio Evaluation are never automatically converted into public copy.

## 3. Current implementation

The following are implemented on `main`:

- bilingual Japanese / English site
- `publishing/publications.json` public publication registry
- `publishing/figures.json` public figure registry
- `publishing/series.json` recurring series registry
- `scripts/build_publication_site.py` registry-driven static builder
- generated JA / EN homepages
- generated JA / EN Research indexes
- generated Market Watch and series landing support
- generated sitemap / hreflang
- generated JA / EN / aggregate RSS
- Preview workflow using the same Builder as Production
- production-candidate build from exact Git ref / SHA
- exact-target-SHA approved deploy
- FTPS deploy to Lolipop

The major architecture rule is:

**Registry / approved public source → Builder → `site/`**

Do not maintain homepage, Research index, Market Watch index, sitemap and feeds as independent manual truths.

## 6. Public publication registry

`publishing/publications.json` is the machine-readable registry for public editions.

A publication edition records at minimum:

```yaml
publication_id: scmr-YYYYMMDD-NNN
language: ja
edition: japanese
slug: example
title: ...
summary: ...
content_type: theme_analysis
content_type_label: テーマ分析
themes: [defi, market-structure]
published_at: 2026-09-01T12:26:00+09:00
updated_at: 2026-09-01T12:26:00+09:00
as_of: 2026-08-31
status: published
article_path: site/ja/research/example/index.html
hero_figure: null
related_publications: []
homepage:
  eligible: true
  priority: 50
  lead_candidate: false
```

The same `publication_id` can have JA / EN editions.

Internal Gate status, private reviewer comments and sensitive evidence do not belong in this public registry.

## 7. Series / Market Watch model

`publishing/series.json` defines recurring public observation series.

Current registered series:

`base-tokenized-stock-yield-watch`

Market Watch is not a manually curated directory tree. The Builder generates:

```text
/ja/market-watch/
/en/market-watch/
/ja/series/<series_id>/
/en/series/<series_id>/
```

from `series.json` plus matching publication entries.

A series can exist with zero published entries. Once matching short briefs are registered, they appear automatically in the series projection.

## 8. Long-form Research publication lane

Ordinary Research remains approval-heavy:

```text
internal Research
→ public draft
→ Evidence / freshness / factual review
→ compliance / conflict review
→ public edition
→ public registry
→ Builder
→ Preview
→ visual / link QA
→ exact SHA
→ explicit human publish request
→ production deploy
```

A Git commit or merge to `main` alone is not permission to publish ordinary Research.

## 9. Recurring automatic short-form lane

A separate lane is being introduced for time-sensitive observations from scheduled patrols.

Target examples:

- notable DeFi protocol / TVL / liquidity changes
- abnormal volume / liquidity / market-flow observations
- X / SNS trend acceleration
- Meme-market attention / liquidity changes
- new public on-chain facts worth recording quickly

Flow:

```text
scheduled patrol
→ observation evidence
→ public-short-brief generator
→ pre-approved series profile
→ automatic public-safe validation
→ public article + registry entry
→ Builder
→ Market Watch / series / RSS projection
→ production deploy
```

The auto lane must fail closed if any required evidence or policy field is missing.

It must never publish:

- BUY / SELL instructions
- portfolio sizing / entry / exit decisions
- undisclosed holdings
- private or paid-source content that cannot be publicly reproduced
- unverified rumors as facts
- confidential data
- secrets
- manipulative promotion or language intended to create exit liquidity

A new auto series requires explicit human activation. Once activated, individual entries may be published automatically only inside that fixed series contract.

See `publishing/AUTO_PUBLICATION.md`.

## 10. Automatic publication contract

Short briefs should use a small deterministic schema rather than unrestricted AI prose.

Minimum fields:

```yaml
publication_id: mw-YYYYMMDD-HHMM-<series>
series_id: ...
language: ja
content_type: market_watch
observed_at: ISO-8601 JST
as_of: ISO-8601 JST
title: ...
summary: ...
what_changed: ...
evidence:
  - source: ...
    observed_at: ...
    fact: ...
limitations: ...
disclosure: ...
auto_publish_profile: ...
```

Machine validation checks identity, timestamps, source presence, freshness, series allowlist, text limits and banned internal fields before the public repo accepts the item.

## 11. Builder

Canonical builder:

`scripts/build_publication_site.py`

Current outputs include:

- homepages
- Research indexes
- Market Watch indexes
- series landing pages
- sitemap / hreflang
- RSS feeds

Preview and Production invoke the same Builder to prevent rendering drift.

Builder validation currently covers duplicate publication editions, slug collisions, invalid language / dates, missing article files, missing figures and broken related-publication references. Series registry validation also checks required series fields.

The auto-publication lane should extend this validation rather than create a second rendering system.

## 12. Figure / data model

`publishing/figures.json` is the public figure registry.

Public figures preserve `figure_id`, `publication_id`, title, `as_of`, source / method summary and public file paths.

Approved SVG remains a primary web artifact where appropriate. Raster derivatives can be produced from the same approved spec / data for other channels.

Measured Data Figure, Analytical Diagram, Editorial Visual and External Figure must remain distinguishable in provenance.

## 13. Bilingual model

Japanese and English are first-class public editions.

Equivalent editions share `publication_id` and preserve numerical values, Evidence meaning, Figures, material limitations and disclosure semantics.

A short-form auto series does not require simultaneous JA / EN publication unless the series profile says so. Missing language editions must not be fabricated by route inference.

## 14. RSS / discovery

The Builder generates feeds from the public registry.

Current targets:

- Japanese feed
- English feed
- aggregate public feed

Market Watch entries should naturally enter these feeds when their registry status is `published`.

Future type-specific feeds can be added without changing the article source model.

## 15. Production deployment

Production deploy is FTPS to the dedicated Lolipop document root for `signaetstructura.com`.

Ordinary Research:

```text
exact approved SHA
→ publication/publish-requests/active.json
→ Deploy Approved Publish Request workflow
→ checkout exact target SHA
→ Builder
→ validation
→ manifest
→ FTPS
```

The automatic Market Watch lane must use the same Builder and deployment target. It should not maintain a parallel copy of HTML or bypass validation.

Credentials remain only in GitHub Actions secrets or equivalent secret storage.

## 16. Release provenance

Production release evidence should identify:

- target source SHA
- generated files / hashes
- production target
- publication IDs or auto-series entry IDs
- deployment result
- publication time

Automatic short posts should retain machine-readable receipts even when no human reviews each individual item.

## 17. Security / compliance boundary

Never place in this public repository:

- API keys / passwords / private keys / seed phrases
- raw private X API payloads that are not public-safe
- unpublished portfolio holdings or trading intentions
- internal Candidate / Evaluation / Intent artifacts
- confidential evidence
- private reviewer comments
- non-public personal information

Public Market Watch should describe observable market conditions, not use the publication surface to influence a market.

## 18. Scaling model

The system should scale by adding registry items, not by adding hand-maintained index pages.

```text
new Research / Watch item
→ one public content object
→ one registry entry per language edition
→ optional figure / series references
→ Builder projections everywhere else
```

This applies to future Themes, Case Studies, Data and SNS Trends as well.

## 19. Current next implementation boundary

The Web-side Market Watch projection already exists.

Remaining work for automatic patrol publication is primarily:

1. define and validate the public short-brief package
2. add a pre-approved auto-series profile registry
3. add a Web-side intake workflow
4. connect `sc-crypto-ops` patrol generators to that intake
5. retain public deployment receipts
6. test with non-trading, factual shadow entries before enabling unattended production

This work belongs to the existing Public SC Markets Research / Market Watch scope; it does not create a new investment architecture.
